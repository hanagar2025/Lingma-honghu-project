# 鸿鹄

按真实账本出执行单。一个页面，一个输入框。

战略写在 `战略组合2026-2030/战略书-v1-草案.md`，不写在代码里。代码只做四件事：

1. 账户与纪律：读账本、持仓价格和链上数据，按《半年计划》算出当天的执行单。卖出只由资金分和趋势触发；单票和相关环节的占比上限只限制加仓；净值指数对着观察线、预警线、停手线三条线。价格两处来源对不上、账本过期，就不出指令。系统不下单。见下面「执行单的规则」。
2. 收件：委员会在页面上交持仓截图、成交记录、下单前的一行字。账本、成交、意向、截图只存在服务器的私有目录里，不进仓库。
3. 规则指纹：现行规则登记成清单并取指纹，任何改动都会在基线文件的 diff 里显形。
4. 简报：每个交易日把持仓的资金分、趋势分和卖出条件，净值指数离目标和三条线多远，已登记的预判对照，记分牌，汇成一页。简报不产生买卖指令，也不另起口径，读数都取自执行单。
5. 链上数据与定时汇总：每个交易日把 AI 主线 15 个环节核心股的日线、主力资金、融资余额、最新业绩拉下来累积；到点由汇总机器人算分、排序、核对规则条件，推到页面。只算数，不做判断，不下单。见下面「链上数据与定时汇总」。

## 部署到服务器

服务器连不上 GitHub，所以在自己的电脑上打包、拷上去、在服务器上安装。服务器上只需要 systemd，不需要 npm，不需要 git。没有 Node.js 18 以上时，安装脚本从阿里云镜像下载一份放在 `/opt/honghu/node`，只给鸿鹄用，不动系统里的 Node.js。

在自己的电脑上，仓库根目录：

```bash
DEPLOY_HOST=<服务器公网地址> DOMAIN=<域名> DEPLOY_KEY=<登录私钥路径> ./scripts/ship-from-mac.sh
```

这一条命令做四件事：打包并在本机试跑；拷到服务器；在服务器上运行 `scripts/install-on-server.sh`；从公网核对线上跑的是刚发的这一版。加 `DRY_RUN=1` 只做第一件。

安装脚本在服务器上做的事：

| 位置 | 内容 |
|---|---|
| `/opt/honghu` | 程序（一个后端文件加页面） |
| `/var/lib/honghu` | 私有数据：账本、成交、意向、截图。只有服务账号能读 |
| `/opt/honghu/py` | 两个扫描脚本原件和已有的历史读数。需要服务器上有 Python 3.8 以上，没有时这两份读数出不来，其余照常 |
| `/etc/honghu.env` | 三个口令（委员会、战略侧、汇总机器人），第一次安装时生成；老的口令文件里没有机器人口令时补一行。只有 root 能读 |
| `honghu.service` | 系统服务，只监听本机端口 5080 |
| nginx 或 Caddy 的站点配置 | 把域名接到本机端口。接到正在占用 80/443 的那一个上；两个都没有时装 Caddy |

重复运行是安全的：口令和数据不会被覆盖，nginx 或 Caddy 的现有站点不会被改动，新配置检查不通过会自动还原。证书就绪之前，域名只返回 503，不会用不加密的连接传口令和账本。

三个前提，脚本会检查并写明还差哪一个：

1. 域名有一条 A 记录指向这台服务器。
2. 服务器在中国大陆时，域名已经备案。没有备案的域名，80 和 443 端口的请求会被拦截，证书也申请不下来。
3. 机器上有 certbot（配 nginx 用）。

已验证与未验证：打包、安装脚本的前四步、nginx 站点的三种情形（无证书、证书损坏时还原、有证书时转发）、接入已在运行且有别的站点的 Caddy（转发正常、原站点不受影响、配置检查不通过时还原）在 Ubuntu 24.04 上演练过，其中 systemd 用替身模拟，证书用自签名。真实 systemd、真实证书申请没有跑过。

## 每天自动做的事

服务器自己完成，不依赖别的定时任务：

| 时间（北京时间，交易日） | 做什么 |
|---|---|
| 09:20 | 重算执行单与简报，补上一交易日的留底。有指令才推送 |
| 10:30 | 按实时价复核。有指令才推送 |
| 15:50 | 收盘后重算、留底，推送当日执行单与简报。排在 15:35 拉日线和主力资金之后，用的是当天的读数 |
| 确认一份新持仓之后 | 按新账本立即重算并推送 |

推送通道和截图识别服务的密钥由委员会在页面「设置」里填，存在服务器私有目录，页面读不回。没填推送通道时不推送，页面照常更新；没填识别密钥时截图留给战略侧人工识别。

截图识别的结果和人工识别走同一条路：必须过勾稽核对，并且由委员会在页面上确认，账本才更新。

简报里的预判登记在 `backend/src/services/insight/config.ts`，写明出处与登记日期，改动走 PR。

## 执行单的规则

口径是《半年计划》第〇、二、三、四、六节，数值登记在 `backend/src/services/dailyDecision/rules.ts` 的 `PLAN` 里，自检核对它与汇总机器人用的是同一套。

卖出，只有三种来历：

| 条件 | 动作 |
|---|---|
| 资金分 C 连续 2 个交易日不高于 1 | 卖出一半。一轮只减一次，C 回到 2 以上才重新计 |
| 资金分 C 为 0 | 清仓 |
| 收盘从 60 日线上方跌到下方，且 5 日融资余额在降 | 清仓 |
| 策略方登记的收盘线（带卖出档位）成立，或策略方直接登记 | 按登记的档位：全部、一半、三分之一 |

占比再高也不卖。单票上限（证据分 E=6 为 20%、E=5 为 15%、E=4 为 10%、E 不高于 3 不加）和相关环节（光模块加 PCB）30% 只限制加仓。

买入由策略方登记目标占比，系统不自己生成。每条逐项过规则，过不了的列在「被规则挡住的买入」里并写明原因：净值基准、三条线、同一只股票有没有未完成的卖出、证据分是否定稿、入场条件（E 不低于 5、无基本面扣分、成交额不低于 10 亿）、单票上限、相关环节余量、股票仓位上限、账内现金。

三条线按净值指数（基准日为 100）：

| 线 | 触及之后 |
|---|---|
| 观察线 95 | 不开新仓，已有持仓照规则 |
| 预警线 90 | 股票仓位降到 50% 以下；切换到备用目标（单票上限 10%，股票不超过 50%），不自动切回 |
| 停手线 85（最高到过 121 后为 100，到过 147 后为 125） | 停止买入，2 个交易日内股票仓位降到 30% 以下 |
| 目标 178 | 股票仓位降到 30%，不再开新仓 |

触线后降哪几只由策略方登记，执行单只写要求和现在的仓位。

缺数据时：买入一侧缺的项按 0 分算；卖出条件只有确定成立才生成指令，核对不了的列在「核对不了的和待定稿的」里，不算成立，也不算不成立。收盘当天融资余额还没公布，那时的资金分是初算，初算成立的卖出条件等次日盘前定稿仍成立才生成指令。

指令有效期：触发后的下一个交易日执行，没成交顺延 3 个交易日，之后作废。条件还成立时不自动重发，由策略方决定要不要再登记。成交以账本为准：确认新的持仓截图后，已完成的指令自动结束。

指令簿存在私有目录 `<DATA_DIR>/chain/orders.json`。接口：

```bash
# 策略方登记卖出（档位 ALL / HALF / THIRD）或买入（目标占比，小数）。理由里只写比例和读数，不写股数和金额
curl -X POST https://<域名>/api/orders -H "Authorization: Bearer <战略侧口令>" -H 'Content-Type: application/json' \
  -d '{"code":"688347","name":"华虹公司","side":"BUY","targetWeight":0.1,"reason":"E=5，资金与趋势都成立","source":"半年计划第四节"}'
# 策略方撤销，或委员会否决
curl -X DELETE https://<域名>/api/orders/<指令编号> -H "Authorization: Bearer <委员会口令>"
# 切换或撤回备用目标
curl -X PUT https://<域名>/api/orders/backup -H "Authorization: Bearer <战略侧口令>" -H 'Content-Type: application/json' -d '{"on":true,"why":"<原因>"}'
```

带卖出档位的收盘线在登记盯线时多写一个 `"sell":"THIRD"`（见下一节的例子），只有收盘跌破的线能带。

## 链上数据与定时汇总

分工：后端管数据，机器人管到点汇总，判断和决定由策略方写，委员会查看和否决，下单由委员会本人操作。系统不下单。

环节和核心股以 `scripts/ai-mainline-map.py` 为准，`scripts/chain-universe.py` 把它导出成 `backend/src/services/chain/data/universe.json`，CI 核对两边一致。打分口径是《半年计划》第二节，S1–S5 五个切换条件只读脚本输出的 `triggers`，汇总层不另算一套。

后端自己到点做的事（北京时间，交易日）：

| 时间 | 做什么 |
|---|---|
| 08:20 起 | 拉上一交易日的融资余额（交易所盘后公布），没出来就每 10 分钟再试 |
| 09:30–15:00 | 每 5 分钟核一次已登记的线，第一次越线时推送一条 |
| 11:35 | 拉午间快照：现价、成交额、上午主力净流入 |
| 15:35 | 拉当日日线和主力资金，随后运行 `ai-mainline-map.py` |
| 16:22 | 运行 `market-scan.py`（全市场，十来分钟） |
| 各汇总时点后 15 分钟 | 该到的汇总没到，推送一条提醒 |

取不到数时怎么办：

- 日线：东方财富取不到时改用腾讯，照实记下哪几只是腾讯的。
- 主力净流入只有东方财富一个来源，取不到就记“缺”，该项按不成立算，不补不猜。同一来源连着 3 只取不到，这一轮就不再去碰它；收盘后的窗口内每 5 分钟只补缺的那几只。
- `ai-mainline-map.py` 取不到数时不失败，把缺项记在存档的 `missing` 字段里：缺哪几只、主力过半缺失时环节名次沿用哪一天的。汇总把这些原样写出来。带缺项的那份，等后端自己的拉数齐了（说明来源恢复了）再重跑，一天最多重跑 2 次。

数据存在私有目录 `<DATA_DIR>/chain/`，按股票逐日追加，已有的日期不改写。免费来源（东方财富、新浪、腾讯）没有服务等级保证：主力资金只有一个来源，无法交叉核对；收盘价用腾讯做第二来源，对不上的记在缺口里随汇总一起显示。

汇总机器人的时点（北京时间）：

| 时点 | 内容 |
|---|---|
| 08:40 盘前 | 融资公布后资金分定稿，持仓逐只对卖出条件，候选对入场条件，三条线 |
| 11:40 午间 | 上午主力流向、现价对均线、已登记的线 |
| 16:20 收盘 | 当日资金分（融资未公布，标为初算）、环节排序、S1–S5 |
| 16:40 全市场扫描 | `market-scan.py` 的结果 |
| 周五 16:50 周度 | 环节周度排序、换仓条件核对 |

机器人在本机试跑（不需要 Cursor 凭证，只算不推）：

```bash
cd agents/honghu-digest && npm ci
npm run selftest                          # 打分、规则核对、五份汇总，全部离线
HONGHU_SERVER_URL=http://127.0.0.1:5000 HONGHU_AGENT_TOKEN=<本机后端的 BOT_TOKEN> npm run digest -- close --dry
```

去掉 `--dry` 就推到页面。部署到 Cursor 托管由委员会在自己的电脑上做，口令在隐藏提示里粘贴，不写进代码、日志和对话：

```bash
cd agents/honghu-digest
npx agent-sdk login
npx agent-sdk deploy
npx agent-sdk secret set honghu-digest HONGHU_AGENT_TOKEN   # 粘贴服务器 /etc/honghu.env 里 BOT_TOKEN 的值
```

口令的权限：

| 口令 | 能做什么 |
|---|---|
| `BOT_TOKEN`（机器人） | 读链上数据、仓位占比和净值指数；推汇总。读不到账本、成交、截图 |
| `AGENT_TOKEN`（战略侧） | 另可登记盯线和供给冲击、对汇总写决定、登记和撤销执行单上的指令、切换备用目标；机器人缺席时手动补推汇总 |
| `COMMITTEE_TOKEN`（委员会） | 另可否决汇总和执行单上的指令、设净值基准 |

给机器人的接口里只有占比和净值指数，没有股数和金额；带这些字段的汇总后端拒收。净值指数的基准（100 对应的那一天）由委员会用自己的口令设一次，金额只落在服务器上：

```bash
curl -X PUT https://<域名>/api/chain/base -H "Authorization: Bearer <委员会口令>" -H 'Content-Type: application/json' -d '{"totalAssets": <基准日总资产>, "at": "<基准日>"}'
```

盯线和供给冲击由策略方登记（整组替换），每条都要写规则原文的动作和出处：

```bash
curl -X PUT https://<域名>/api/chain/watch -H "Authorization: Bearer <战略侧口令>" -H 'Content-Type: application/json' \
  -d '{"lines":[{"code":"300308","name":"中际旭创","basis":"close","op":"below","level":"ma20","and":"main_out","action":"次日卖三分之一","sell":"THIRD","source":"<出处>"}]}'
curl -X PUT https://<域名>/api/chain/flags -H "Authorization: Bearer <战略侧口令>" -H 'Content-Type: application/json' \
  -d '{"flags":[{"code":"688041","name":"海光信息","reason":"供给冲击","source":"半年计划第二节","since":"2026-11-20"}]}'
```

已验证与未验证：拉取、打分、五份汇总、机器人定时任务到工具的调用，在开发机上对真实行情和本机后端跑通过。大陆服务器访问这几个来源、服务器上的 Python、Cursor 托管到域名的连通，没有验证过。

## 输入框怎么写

| 用途 | 写法 |
|---|---|
| 下单前登记 | `计划卖出 中际旭创 600股 单票归位` |
| 成交 | `卖出 中际旭创 600股 509.89`，一行一笔；或发成交截图 |
| 持仓 | 发持仓截图：选择图片、粘贴或拖进来。识别结果过了勾稽核对后，回到页面确认，账本才更新 |
| 其他 | 直接写，原样转给战略侧 |

## 边界

- 执行单是下单计划，不是成交记录。
- 系统不下单，也不自己生成买入。买入由策略方登记目标占比，执行单逐条过规则后列出或挡住。简报是读数，不是指令。
- 规则与阈值的改动须经委员会裁定，并重新生成规则基线。
- 金额、股数、现金不进公开仓库。
